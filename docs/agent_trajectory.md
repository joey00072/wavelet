# Agent Trajectory Artifacts

Custom agent rollouts may run message loops, tools, sandboxes, and rewards, but
the trainer-facing artifact should stay token based. Runtime text is useful for
debugging; trainable targets should come from the model boundary that produced
token ids and logprobs.

Use `wavelet.orchestrator.agent_trajectory.TokenSegment` for each model turn:

- `prompt_ids`: token ids sent to the model for that turn
- `output_ids`: token ids generated by the model
- `output_logprobs`: rollout-time logprobs aligned with `output_ids`
- `prompt_loss_mask`: optional mask for prompt tokens, defaulting to all false
- `output_loss_mask`: optional mask for generated tokens, defaulting to all true
- `turn_id`: optional stable id for trace/provenance joins

Then call `merge_token_segments`. It merges a later turn only when the new
prompt exactly extends a previous `prompt_ids + output_ids` prefix. If the exact
prefix cannot be proven, it starts a separate trainable sample instead of
guessing from decoded text. This keeps tool observations and other non-model
context masked while preserving generated tokens and logprobs.

Agent harnesses should keep bulky debugging data in sidecars or metadata:
messages, tool calls, tool results, verifier traces, parser errors, sandbox
paths, screenshots, and timing. The compact trainer path should contain token
ids, target ids, loss masks, rollout logprobs, rewards, advantages, policy step,
trajectory/session ids, and enough metadata to replay or inspect the rollout.

When a custom rollout emits trainer rows, use these metadata conventions:

- `task`: task name plus `example_id`
- `harness`: execution adapter name, type, and version when known
- `rollout`: `group_key`, `rollout_key`, `trajectory_id`, `num_turns`,
  `tool_calls`, `elapsed_sec`, `error`, `is_truncated`, `stop_condition`, and
  `reward_components` when available
